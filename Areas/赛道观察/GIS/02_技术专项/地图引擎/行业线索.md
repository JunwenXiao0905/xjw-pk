# 地图引擎行业技术现状报告

> 信息核实截至 2026 年 8 月，关键结论附信源（§10）

地图引擎正在经历一次底层换代：浏览器端的渲染接口从 WebGL2 走向 WebGPU，引擎内部的空间计算核心开始用 Rust 重写。本报告梳理这条主线的行业现状——新引擎做到哪一步了、主流引擎迁移到什么程度、哪些基础设施已经可生产使用、还有哪些风险需要跟踪。

阅读前需要澄清一个容易混淆的概念：**Rust 和 WebGPU 是两个独立的维度，不是一回事。** Rust 是实现语言，可以用来写空间算法、瓦片服务或渲染器；WebGPU 是图形接口，Rust、C++、TypeScript 都能调用。行业里的真实组合各有取舍——Martin 只有 Rust 没有 WebGPU，deck.gl 只有 WebGPU 没有 Rust，Navara 的核心用 Rust 写、渲染却交给 Three.js。本报告把两者当作观察维度分别评估，而不是当作一条捆绑的技术栈。

## 1. 核心结论

1. **渲染底座的换代前提已成立**：2025 年 11 月起，WebGPU 在 Chrome、Edge、Firefox、Safari 全部默认启用（§2）。浏览器端第一次有了跨厂商的新一代图形接口，地图引擎升级渲染底座不再受制于浏览器支持。
2. **Rust 的成熟度按产业环节分化**：在瓦片服务与空间数据基础设施环节（Martin、VersaTiles、pmtiles-rs 等），Rust 已是生产可用的主力语言（§3.2）；在渲染内核环节仍处探索期，尚无 1.0 级产品（§3.1）。
3. **新引擎分化出三种架构路线**（§3.1）：全 Rust 渲染内核（Galileo）、TypeScript 框架 + Rust/WASM 空间核心（MapGPU）、Rust/WASM 无头 GIS 核心 + 可替换渲染器（Navara）。其中 Navara 是 2025–2026 年最受关注的新样本（§4）。
4. **主流引擎在渐进迁移，商业 SDK 尚未跟进**：MapLibre Native 已提供官方 WebGPU 后端（可选 Dawn 或 wgpu-native 实现）；deck.gl v9 完成了接口重写但 WebGPU 仍为实验特性；Esri 的 JavaScript SDK 截至 5.1（2026-06）仅支持 WebGL2（§3.3）。开源前沿领先商业主流，这个时间差既是机会窗口，也是赛道节奏不确定性的来源（§7）。
5. **全 Rust 重写成熟渲染器的代价已有前车之鉴**：maplibre-rs——MapLibre 官方孵化过的全 Rust 渲染器——自 2023 年中停滞至今，原作者公开说明单一维护者无法支撑其工程量（§5.1）。这解释了为什么后来者更多选择"Rust 做 GIS 核心、渲染复用现有生态"的路线。
6. **跟踪优先级建议**：Navara → Galileo → MapLibre Native WebGPU 后端 → MapGPU；基础设施层以 Martin 为主。排序理由见 §8。

## 2. 关键前提：WebGPU 浏览器基线（为什么是现在）

| 浏览器 | WebGPU 默认启用 | 时间 |
|---|---|---|
| Chrome / Edge | 是 | 2023-04 起（Chrome 113） |
| Firefox | 是（自 Windows 起） | 2025-07（Firefox 141），Linux 预计 2026 |
| Safari | 是（macOS / iOS / iPadOS） | 2025 秋（Safari 26；初版支持自 18.2，2024 末） |

- 2025-11 四大浏览器全部默认支持：[webgpu.com 报道](https://www.webgpu.com/news/webgpu-hits-critical-mass-all-major-browsers/)、[web.dev 官方博客](https://web.dev/blog/webgpu-supported-major-browsers)、[Firefox 141 发布说明（Mozilla Graphics）](https://mozillagfx.wordpress.com/2025/07/15/shipping-webgpu-on-windows-in-firefox-141/)
- Rust 侧 [wgpu](https://wgpu.rs/) 实现 WebGPU API：原生目标 Vulkan / Metal / D3D12 / OpenGL，Web 目标经 WASM，"一次实现、跨端 + Web"的工程闭环已可用
- 含义：WebGPU 地图引擎此前最大的制约（浏览器支持不全）已经消除，剩余风险集中在应用生态与工程成熟度（§7）

## 3. 行业现状：三个环节、三种成熟度

按产业分工分三个环节观察：渲染内核（谁在造新引擎）、瓦片服务基础设施（数据链路是否就绪）、主流引擎演进（存量玩家迁移到什么程度）。

### 3.1 渲染内核：三种架构路线并存

| 路线 | 代表项目 | Rust 用在哪 | 渲染后端 |
|---|---|---|---|
| A. 全 Rust 渲染内核 | maplibre-rs（停滞）、Galileo | 渲染 + 逻辑全在 Rust | wgpu 直连 |
| B. TS 框架 + Rust/WASM 空间核心 | MapGPU | 空间计算核心 | WebGPU / WGSL（TS 侧调度） |
| C. Rust/WASM 无头 GIS 核心 + 可替换渲染器 | **Navara** | GIS 核心逻辑（坐标 / LOD / 椭球 / 切片） | 当前 Three.js，设计上可替换 |

要点：

- 路线 A 最"纯粹"但工程量最大——maplibre-rs 的停滞是直接证据：原作者 [maxammann 评估](https://github.com/maplibre/maplibre/issues/424)，仅 SDF 字体渲染的概念验证就需要从 C++ 翻译约 1 万行代码，单一维护者不可持续。Galileo 是该路线下唯一持续活跃的通用库
- 路线 B / C 代表另一种判断：**Rust+WASM 的价值最先在"空间计算核心"兑现，渲染层可以后置**——即便渲染仍走 WebGL2 生态（Three.js），把 GIS 核心逻辑用 Rust 重写的收益也已经成立

### 3.2 瓦片服务基础设施：最成熟的环节（Rust 已是主力语言）

| 项目 | 定位 | 活跃度 | 备注 |
|---|---|---|---|
| [Martin](https://github.com/maplibre/martin) | PostGIS / GeoJSON 动态矢量瓦片服务 + MBTiles / PMTiles | 高：2025-09 发布可嵌入 Core Library（插件系统、全异步），2026-08 连发三版 | MapLibre 官方项目，事实标准 |
| [VersaTiles](https://versatiles.org/) | 全链路开源瓦片栈（server + library + CLI） | 稳定 | MBTiles / PMTiles 等格式互转 |
| [pmtiles-rs](https://github.com/stadiamaps/pmtiles-rs) | PMTiles v3 的 Rust 实现 | 稳定 | Stadia Maps 维护，Martin 生态采用 |
| [tileserver-rs](https://github.com/vinayakkulkarni/tileserver-rs) | 单二进制瓦片服务器（+ Nuxt 4 前端），PMTiles / MBTiles / PostGIS / COG / STAC / OGC API | 中：个人项目 | [tileserver.app](https://tileserver.app/)；tileserver-gl 的 Rust 替代，与 Martin 的成熟度不在一个量级 |

补充事件：MapLibre 2026 发布新矢量瓦片格式 **MLT（MapLibre Tile）**，其参考解析器为 Rust 实现（QGIS 集成即基于它），PMTiles 自 1.9.0 支持 MLT 存储及与 MVT 互转（[MLT 实现状态](https://www.maplibre.org/maplibre-tile-spec/implementation-status/)）。Rust 在瓦片格式标准层的地位进一步坐实。

### 3.3 主流引擎演进：渐进迁移，商业侧未动

| 引擎 | 渲染现状 | WebGPU 进展 |
|---|---|---|
| MapLibre Native（C++） | Metal / Vulkan / OpenGL | **官方 WebGPU 后端**：iOS（CMake preset：`ios-webgpu-dawn` / `ios-webgpu`）与 Android（Gradle flavor）双平台，Dawn（C++）与 wgpu-native（Rust）双实现；2025-09 官方通讯官宣（Birk Skyum 贡献）；[roadmap](https://maplibre.org/roadmap/maplibre-native/webgpu/) 含 Web 目标 |
| MapLibre GL JS（TypeScript） | WebGL2 | 未切换；官方 WebGPU 精力集中在 Native 侧 |
| deck.gl / luma.gl | WebGL2 默认 | v9 按 WebGPU 兼容接口重写；WebGPU 仍实验性、未 production-ready（[官方开发指南](https://deck.gl/docs/developer-guide/webgpu)） |
| Esri ArcGIS Maps SDK for JavaScript | WebGL2（[系统要求](https://developers.arcgis.com/javascript/latest/system-requirements/) 明确仅支持 WebGL2） | 截至 5.1（2026-06）无 WebGPU 支持、无公开承诺。同期 5.0 新增 Gaussian Splat Layer——高保真 3D 是全行业共同方向，但渲染底座尚未换代 |

## 4. 重点解析：Navara —— Re:Earth 团队的可扩展 3D 地图引擎

### 4.1 定位

官方一句话：**高度可扩展（highly extensible）的通用 3D 地球地图引擎**——把卫星影像、地形、3D 城市模型、矢量数据等真实 GIS 数据流式加载到浏览器中的 3D 地球上，主打照片级渲染。官方明确其目标是消除传统地图引擎"完善的声明式 API（易接入难扩展）vs 深度底层控制（强大但门槛高）"的取舍。

- 仓库：https://github.com/reearth/navara
- 文档：https://navara-docs.netlify.app/ ；示例：https://navara-preview.netlify.app/

### 4.2 背景与团队

- 开发方：**Eukarya 株式会社**（日本），开源 WebGIS 平台 [Re:Earth](https://reearth.io) 背后的团队
- 生产背景：Eukarya 承接日本国土交通省 [PLATEAU 项目](https://eukarya.io/ja/works/plateauview)（3D 城市模型）的 PLATEAU VIEW 2.0 建设。**Navara 有政府级生产场景和商业团队供养，不是纯社区实验**
- 演进路径：Re:Earth Visualizer 早期基于 CesiumJS，团队转向自研引擎；前身是 Three.js 系的 reearth-three，FY2024 起重新架构为 Navara（仓库内仍保留 `navara_three` 包结构，可见其延续性）
- 公开节奏：2025-11 [FOSS4G 2025 议题](https://talks.osgeo.org/foss4g-2025/talk/RM9RHS/)（Keiya Sasaki）介绍 headless 架构；随后开源仓库公开，登上 GitHub Trending（Trendshift 收录）；官方公告见 [Eukarya 发布文](https://note.com/eukarya/n/n27427d613323)（日文）与 [Medium 英文版](https://medium.com/@eukarya/toward-a-future-where-everyone-can-experience-data-through-navara-the-next-generation-map-engine-66444a60378b)

### 4.3 架构

核心设计决策：**GIS 引擎与渲染引擎完全解耦**（FOSS4G 议题原话：fully decoupling the GIS engine from the rendering engine）。

- **Rust + WebAssembly 构成无头（headless）核心**：坐标变换、LOD 管理、椭球数学、瓦片调度等复杂可复用 GIS 逻辑全部在 Rust 核心中实现
- **渲染委托给外部 CG 渲染库**：当前为 Three.js，**设计上可替换**，官方计划扩展至其他渲染引擎与平台
- 关键辨析：Navara 属于 §3.1 的路线 C。它验证的是 "Rust+WASM 作为 GIS 核心"，**不是** "Rust+wgpu 作为渲染器"——目前渲染通路走 Three.js（WebGL2 生态）。把 Navara 简单归入 "Rust+WebGPU 渲染引擎" 是不准确的

### 4.4 四层可扩展性 API

| 层级 | 能力 | 面向人群 |
|---|---|---|
| 1. Declarative API | 底图 / 地形 / 3D Tiles / 矢量数据配置式接入；mesh、effect、light 可声明式插入 | 所有开发者 |
| 2. Plugins | 即插即用能力包：照片级场景、第一人称行走、DOM 叠加、attribution UI 等；任何人可打包分享 | 所有开发者 / 生态 |
| 3. Low-level API | 按属性逐要素样式（FeatureEvaluator）、要素拾取、地形采样、可独立使用的大地测量 / ECEF 数学工具 | 进阶开发者 |
| 4. Custom Descriptors | 自定义 mesh / effect / light 描述符，直达场景图与渲染管线 | 图形工程师 |

### 4.5 生态位与许可

- 许可：Apache-2.0 / MIT 双许可（仓库 README 标注）
- 官方在 MapLibre 社区（OSM Slack #maplibre 频道）参与讨论，与 MapLibre 生态关系密切
- 数据能力覆盖 PLATEAU 3D Tiles 等日本 3D 城市模型标准，与团队自身政务项目形成闭环

### 4.6 成熟度评估

- 阶段：**早期（pre-1.0）**——文档站尚在 netlify 预览域、示例与文档仍在快速变动
- 但属于"有供养的早期"：商业团队 + 政府生产场景 + 明确的接替 CesiumJS 战略动机
- 风险：渲染层依赖 Three.js 的路线在"性能天花板"上尚未被大规模验证；插件生态刚刚起步，尚无第三方贡献证据

### 4.7 对行业的意义

1. 证明 **Rust+WASM 正在成为 GIS 核心逻辑的默认选型**——即使渲染层暂时留在 JS 生态，核心重写的收益也已成立
2. 其"渲染器可替换"设计意味着未来可能出现 wgpu / WebGPU 渲染后端，是观察路线 C 与路线 A 汇合的关键样本
3. 高保真 3D 方向（照片级、第一人称、大气/云/夜景）与 Esri 的 Gaussian Splat Layer 相互印证：**下一代地图引擎的竞争焦点正在从"二维瓦片渲染性能"转向"三维照片级场景 + 可扩展性"**

## 5. 项目档案

### 5.1 maplibre-rs（已停滞）

- 定位：跨平台矢量地图渲染器（Rust + wgpu），2022-05 由 mapr 更名并入 MapLibre 组织（[类别档案](https://maplibre.org/categories/maplibre-rs/)）
- 现状：最后一次官方月报为 2023-06（自认近乎停滞）；2024-11 原作者公开讨论存续与品牌去留（[issue #424](https://github.com/maplibre/maplibre/issues/424)，已关闭）；此后官方通讯与仓库均无实质推进
- 启示：MapLibre 同时维护 GL JS（TypeScript）与 Native（C++）双实现已是极限，第三条全 Rust 路线在没有专项资源时不可持续——这是路线 A 工程成本最直接的证据
- 仓库：https://github.com/maplibre/maplibre-rs

### 5.2 Galileo（路线 A 唯一持续活跃的通用库）

- 定位：通用跨平台 GIS 渲染库（Rust + wgpu），栅格 + 矢量瓦片，宣称百万级要素 60 FPS；桌面三平台 + wasm Web 目标
- 现状：持续迭代，0.x 阶段，生态建设期；无 MapLibre Style 完整兼容包袱，走通用库路线
- 仓库：https://github.com/galileo-map/galileo ；文档：https://docs.rs/galileo

### 5.3 MapGPU（路线 B 产品形态样本）

- 定位：WebGPU 原生 GIS 引擎；TypeScript API + WGSL + Rust/WASM 空间核心，单一 npm 包分发；双投影 3D 地球、OGC 适配器，支持矢量瓦片 / 栅格 / 地形 / 3D Tiles，宣称百万级要素渲染
- 现状：新项目（近期 [r/webgpu 发布帖](https://www.reddit.com/r/webgpu/comments/1se8xdj/i_built_a_webgpupowered_map_engine_renders_1m/)），单人主导；许可证与商业模型的公开信息不足，采用前需自行核实
- 站点：https://mapgpu.dev/ ；仓库：https://github.com/mgurbuz-tr/mapgpu

### 5.4 MapLibre Native WebGPU 后端（主流演进风向标）

- iOS / Android 均已支持：可选 Dawn（C++）或 **wgpu-native（Rust）** 实现，构建期通过 CMake preset / Gradle flavor 选择（[iOS 文档](https://maplibre.org/maplibre-native/docs/book/platforms/ios/ios-webgpu.html)、[Android 文档](https://maplibre.org/maplibre-native/docs/book/platforms/android/android-webgpu.html)）
- wgpu 路线与 Slint SDK 等 UI 框架集成方向相关（[issue #3869](https://github.com/maplibre/maplibre-native/issues/3869)）
- 2025-09 官方通讯官宣该后端（Birk Skyum 贡献）；当前定位仍是可选后端而非默认

## 7. 风险与不确定性

- **渲染内核无 1.0 级产品**，三种路线未收敛；任何单一下注都有选错路线的风险
- **路线 A 成本已被验证过高**：maplibre-rs 停滞表明全 Rust 重写 MapLibre 级渲染器非单一维护者可承载
- **商业引擎未入场**：Esri 截至 2026-06 无 WebGPU 承诺。WebGL2 仍满足多数需求，迁移动力主要来自 3D / 高保真 / 计算密集场景——若这些场景增长不及预期，赛道节奏会慢于社区热度
- **巴士因子**：MapGPU、tileserver-rs 等单人主导项目存在持续性风险；Navara 虽有公司供养，但同样处于早期
- **浏览器残余问题**：Firefox Linux 版 WebGPU 预计 2026 年内解决，跨平台一致性仍有尾巴

## 8. 跟踪建议

按信息增益从高到低：

1. **Navara**（渲染内核 · 路线 C）：有公司供养、有生产场景、架构独特
2. **Galileo**（路线 A 唯一持续活跃的通用库）
3. **MapLibre Native WebGPU 后端**（主流引擎风向标，重点看 wgpu-native 路线是否成为默认）
4. **MapGPU**（路线 B 产品形态样本；核实许可证与商业模型后再决定升降级）
5. **基础设施**：Martin 为主（官方 + 高活跃），VersaTiles / pmtiles-rs 常规跟踪，关注 MLT 格式演进

maplibre-rs 仅作存档观察：若 MapLibre 官方宣布重启资源投入，再恢复跟踪权重。

## 9. 观察指标（可量化复核）

- 渲染内核项目是否出现 1.0 或生产案例（Navara → PLATEAU 生产迁移；Galileo → 下游采用）
- MapLibre Native 的 WebGPU 后端是否转为默认后端；GL JS 是否出现 WebGPU 路线图
- deck.gl WebGPU 是否转 production-ready；Esri 是否首次公开 WebGPU 计划
- Navara 是否出现第三方插件、第二个渲染后端（尤其 wgpu/WebGPU 方向）
- MLT 格式采用度（QGIS / 编辑器 / 服务端工具链）
- 浏览器残余：Firefox Linux WebGPU 落地（预计 2026）
