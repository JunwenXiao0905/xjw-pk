# 行动主线

> 这是个人当前唯一认可的行动主线,取代了 [[转型路线]] 那套 5 条并列候选。
> 核心转变:从"收集方向"变为"一条带依赖顺序的链"。
> 确立时间:2026-07-27。

## 核心判断(为什么是这条线)
1. **市场验证**:超图 agent 岗的反馈是"**后端为主,agent 能力其次**"——真实招聘需求决定了地基在后端工程,不在 agent 框架本身。
2. **能力匹配**:当前工作(touyou 轨迹数据处理)和这条线的技术栈重叠,工作能喂养地基。
3. **未来押注**:GIS Agent 是 GIS 厂商普遍在做的方向,且 GIS 背景 + agent 能力是稀缺交叉点。

## 两条并行轨道

### 轨道一:工作(主战场,简历主体)
- 深入研究各种数据处理方法
- 强化 Python 处理 GIS 数据的能力(GeoPandas/Shapely/空间分析)
- 研究数据分发、切片服务
- 这条轨道的产出 = 简历主体,**往深做,讲得出故事**

### 轨道二:业余(能力发动机,带依赖链)
一条有依赖顺序的链,每一环只依赖前一环:

```
postgres → postgis → go → gin → 瓦片服务(+压测优化)
       → docker 部署 → agent 最小版 → k8s(遇痛点再学) → 持续迭代
```

#### 链上各环的验收标准(防"假学")

| 环节 | 验收标准(达到才算过关) | 状态 |
|---|---|---|
| postgres | 能独立设计 schema、写复杂查询、理解事务与索引 | ⬜ |
| postgis | 能用空间索引(GiST)、写空间查询、理解 geometry vs geography | ⬜ |
| go | 能独立写一个带 HTTP 服务的程序,理解 goroutine/channel | ⬜ |
| gin | 能用 gin 写 RESTful API,理解中间件 | ⬜ |
| 瓦片服务 | **不是"写完即结束"**:能压测、说出瓶颈在哪、做过优化 | ⬜ |
| docker | 能用 docker compose 把瓦片服务跑起来 | ⬜ |
| agent 最小版 | **调研最多两周死线**,然后必须动手;最小版=能调 LLM + 查 postgis 回答地理问题 | ⬜ |
| k8s | **延后**:遇到"单机扛不住、需要扩缩容"真实痛点再学,不为学而学 | ⬜ |

## 三个必须守住的红线

### 1. agent 产品是能力发动机,不是敲门砖
- 敲门砖是简历上的工作经历(轨道一)
- agent 产品让你在没人盯着时持续练手,能写进简历"个人项目"栏
- **不指望它换 offer,专注做,不盯着"够不够换工作"**
- 心态差决定做产品时是否焦虑

### 2. agent 调研设死线(两周)
- "调研/收集信息"是过去的陷阱模式
- agent 核心难点在工程(调 prompt/token 超限/工具调用失败),不在知识
- **最多调研两周,然后必须写代码,哪怕很丑**

### 3. k8s 延后,docker 先行
- k8s 对个人项目/中小公司通常是过度工程
- 先用 docker compose,遇到真实扩缩容痛点再学 k8s
- 那时是带着问题学,效率高 10 倍

## 已砍掉/降级的方向(显式记录,防漂移)
- ❌ **遥感智能算法**:走到底就是算法岗,与"算法岗不考虑"的判断冲突,砍
- ❌ **地图引擎(作为主攻)**:造引擎岗位全国几百个,单行道;WebGPU 留作 agent 渲染层探索,不单独追
- ⬇️ **空间数据可视化表达**:降级为 agent 产品的表现层,不单独作为方向(单独做场景薄)
- ⬇️ **空间数据工程**:降级为 agent 产品的地基(postgis/go),不单独作为方向

> 上面的砍/降级,不是"不学",是"不作为独立方向平行推进"。它们的能力会自然融入主线的链里。

## 与工作的关系(边界)
- 理想:工作(数据处理/切片)与业余(瓦片服务)**互相喂养**,业余搞懂的能反哺工作
- 边界:业余产品必须是**自己的、可控的、能写进简历"个人项目"**的东西,和工作产出要有清晰分界,避免"分不清在给谁干"
