# 知识笔记编写器

此技能用于编写个人知识库笔记，供日后查阅。

## 主要目标

当用户表示需要添加某个知识点时：

1. 找到最合适的现有章节。
2. 直接在该处插入内容。
3. 保持笔记紧凑、可搜索、结构稳定。

不要默认在文档末尾追加。

## 写作定位

将文档视为：

- 个人参考笔记，
- 面向查询的知识库，
- 长期积累的文件。

不要将其视为：

- 面向初学者的教科书章节，
- 课堂讲稿，
- 聊天式讲解，
- 或励志教程文章。

## 标题规则

标题必须面向检索。

推荐：

- `位置参数与关键字参数`
- `列表解包`
- `TypedDict`
- `useEffect 的执行时机`
- `GeoJSON 与 WGS84`
- `PostGIS SRID`
- `model_dump()`

避免：

- `Python 是什么`
- `理解 React 的核心思想`
- `初识地图投影`
- `从案例看列表展开`

## 放置规则

在编写前对新知识点进行分类。常见类别包括：

- 语言语法，
- 框架行为，
- 运行时机制，
- API 用法，
- 数据模型，
- 前端交互，
- GIS 数据 / 投影 / 坐标系，
- 数据库 / 存储，
- 工程实践，
- 调试或坑点记录。

将新内容插入最近的正确类别下。

如果没有合适的章节：

1. 仅当该内容明确符合笔记的长期结构时，才新增章节。
2. 使用简洁、类似索引的标题。

## 内容规则

为快速查阅而写。只保留高价值信息：

1. 需要记住的具体知识点；
2. 最少的代码、语法、API 形式、数据结构或规则；
3. 关键机制、条件或约束（当它们重要时）；
4. 容易出错的坑点或边界情况。

除非对检索必要，否则不要添加宽泛的介绍。

不要强制每个章节套用同一模板。解释到足以让日后查阅时理解该知识点即可。

## 解释规则

优先使用领域内实际机制来锚定解释。

对于 Python，优先使用：

- 继承
- 方法查找
- `__init__`
- `**data`
- 类创建
- 实例方法绑定

对于前端，优先使用：

- 渲染时机
- 事件流
- 状态更新时机
- props 传递
- effect 执行条件
- 相关的 DOM / 浏览器行为

对于 GIS，优先使用：

- 坐标系
- 投影
- 几何类型
- 空间参考
- 数据格式约束
- 分析工作流步骤

对于工程实践，优先使用：

- 流程顺序
- 真相来源
- 构建 / 运行时边界
- 环境变量加载点
- 接口约定

不要用空话掩盖机制，例如：

- "框架会处理它"
- "库会自动接管"
- "父组件提供了逻辑"
- "地图引擎自动处理"

如果使用了此类表述，必须立即跟上使其成立的具体机制。

当引入新的内部术语（如 `metaclass`、`schema`、`effect`、`SRID`、`projection`）时，要结合已熟知的概念来定义。如果当前理解层次不需要该术语，则延后介绍。

## 方法规则

在记录方法、hook、API 或继承行为时：

1. 说明它来自哪里。
2. 展示调用或行为是如何到达的。
3. 展示等价的直接形式（如有用）。
4. 解释什么接收了输入以及接下来会发生什么。

例如：

- Python 中的父方法解析，
- React 中的 hook 执行条件，
- GIS 中的坐标转换要求，
- API 笔记中的请求 / 响应结构。

## 风格规则

使用：

- 简洁的 prose；
- 直接的陈述；
- 短小的示例；
- 术语优先的写法；
- 贴近代码、数据或机制的解释。

避免：

- 抽象的比喻；
- 不能直接映射到代码或数据的类比；
- 对库、框架或方法使用拟人化语言；
- 当简短的机制导向解释足以说明问题时，不要用冗长的运行时行为叙述。

在可能的情况下，用以下方式解释行为：

- 相关代码；
- 相关数据结构；
- 实际执行它的机制；
- 一句贴近代码或数据的直接陈述。

## 结构规则

仅在目录层级使用类似教科书的组织方式，不在 prose 层级使用。

也就是说：

- 分类可以像一本好的技术书；
- 章节正文应像紧凑的参考手册。

## 输出预期

在编辑时：

1. 选择正确的插入点；
2. 以简洁的参考风格编写新内容；
3. 保持标题一致性；
4. 为将来检索优化。
