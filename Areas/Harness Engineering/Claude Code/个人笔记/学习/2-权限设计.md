# Claude Code使用技巧——权限设计

> 规划了一个长任务，结果总是需要授予权限而不能脱身；
> 授予完全权限又害怕删盘跑路……

Anthropic 官方工程博客披露：用户实际批准了 **93%** 的权限提示。社区把这种状态命名为 **permission fatigue（权限疲劳）**——「几秒钟点一次批准，最后你根本不读就批了」，这本身就是安全风险。
**「全权放手又怕删盘」** ——  `--dangerously-skip-permissions` 模式**清空了 home 目录、抹掉整台 Mac**；**删了生产数据库记录**，这些都是真实的事故。

其实如今的 Claude Code 权限系统在**两端之间提供多个档位**，只要善于利用，就可以做到解脱于权限确认，也不怕事故出现，能够大大提升长任务的效率和安全性。

## 1.1 一次工具调用的权限流程

权限规则由 Claude Code（**harness层**）强制执行，**不是由模型决定**。这是整个权限设计的根基。

一次工具调用（如 `Bash("rm -rf /tmp/x")`）从发起到执行，权限系统按以下顺序介入：

```
                    一次工具调用
                         │
                         ▼
              ┌─────────────────────┐
              │ ① PreToolUse hook   │  前置拦截
              │    （拦不住规则）    │  但拦不住 deny/ask 规则
              └─────────┬───────────┘
                        │
                        ▼
              ┌─────────────────────┐
              │ 受保护路径闸门      │  硬编码 carve-out
              │ （非 bypass 时）    │  写 .git/.claude 等
              │ 早于规则、压过allow │  bypass 放行此格
              └─────────┬───────────┘
                        │
                        ▼
              ┌─────────────────────┐
              │ ② 规则评估          │  硬约束层
              │  deny → ask → allow │  压过一切模式
              └─────────┬───────────┘
                        │
            ┌───────────┴───────────┐
            ▼ 命中规则               ▼ 没命中任何规则
   deny→阻止 / ask→询问      ┌─────────────────────┐
   allow→放行                 │ ③ 权限模式（兜底）  │  决定"无规则时"
                              │  bypass/acceptEdits │  的默认处置
                              │  /default/dontAsk   │
                              └─────────┬───────────┘
                                        │
                                        ▼
                              ┌─────────────────────┐
                              │ ④ 沙箱兜底（仅Bash）│  OS 级强制
                              └─────────┬───────────┘
                                        │
                                        ▼
                                  执行 / 阻止
```

- **受保护路径**：写 `.git`/`.claude` 等关键路径，acceptEdits 等放权模式也照样提示；bypass 放行。
- **规则 = 硬约束**：deny/ask 永远生效，**压过一切模式**。这就是为什么 `ask` 规则即使在 `bypassPermissions` 下也照样弹询问，`deny` 更是任何模式下都会拦截。
- **模式 = 兜底默认**：在"没命中任何规则"时决定怎么办，给 allow 之外的工具一个默认处置。

**权限与沙箱是两层互补防御**：

- **权限**——控制 Claude 能用哪些工具、访问哪些文件/域。作用于**所有工具**（Bash、Read、Edit、WebFetch、MCP 等）。
- **沙箱**——OS 级强制，限制 **Bash 工具**的文件系统与网络访问。仅作用于 Bash 及其子进程。

## 1.2 settings.json 与分层配置

### 1.2.1 权限管理都在 settings.json 里

Claude Code 的所有权限配置都写在 `settings.json` 里，权限相关的字段集中在顶层 `permissions` 对象下：

```json
{
  "permissions": {
    "defaultMode": "acceptEdits",        // 权限模式（见 1.3）
    "allow": ["Bash(npm run test:*)"],   // 规则三态（见 1.5）
    "ask":   ["Bash(git push *)"],
    "deny":  ["Read(./.env)"],
    "additionalDirectories": ["../docs/"]
  },
  "sandbox": { "enabled": true }         // 沙箱（见 1.7）
}
```

前面 1.1 流程里的模式、规则，后面各节讲的沙箱，本质上都是配置这个文件的不同字段。

### 1.2.2 它不是「一个文件」，是分层的一组文件

`settings.json` 不止一个。Claude Code 按固定层级读取多个、合并生效：

```
managed settings    企业强制，最高优先级，无法被覆盖
       ↓
用户级  ~/.claude/settings.json            你这台机器的全局配置
       ↓
项目级  <项目>/.claude/settings.json       随仓库走，团队共享，进版本控制
       ↓
本地级  <项目>/.claude/settings.local.json 个人覆盖，gitignore，不进版本控制
```

**分层的意义**——让不同稳定性的配置各归各位：

| 层级 | 路径 | 适合放 |
|------|------|--------|
| 用户级 | `~/.claude/settings.json` | 你所有项目通用的偏好 |
| 项目级 | `.claude/settings.json` | 跟代码库绑定的团队策略（进 git，团队共享） |
| 本地级 | `.claude/settings.local.json` | 个人临时覆盖（gitignore，不污染团队） |

## 1.3 权限模式与设定途径

### 1.3.1 六种模式

根据官方文档，`settings.json` 中 `permissions.defaultMode` 字段决定 Claude Code 启动时的**初始权限模式**，共有六个可选值，沿自主性↔安全性分布如下：

```
自主性低（安全）                                              自主性高（放手）
dontAsk ── default ── plan ── acceptEdits ── auto ── bypassPermissions
```

| 模式                  | 行为                                                                                                               |
| ------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `dontAsk`           | 只放行 `permissions.allow` 规则集里的，未预批准的工具**自动拒绝**，连问都不问                                                              |
| `default`           | 每个工具首次使用时询问                                                                                                      |
| `plan`              | 只读，**不编辑源文件**（写操作被禁，非询问）                                                                                         |
| `acceptEdits`       | 自动接受工作目录或 `additionalDirectories`目录中的文件编辑命令、 固定的文件系统命令（`mkdir`/`touch`/`mv`/`cp`/`rm`/`rmdir`/`sed`），其他 Bash 仍询问 |
| `auto`              | 分类器自动批准多数工具调用，后台安全检查验证动作符合请求（**研究预览**）                                                                           |
| `bypassPermissions` | `ask` 规则依旧询问，`deny` 规则直接阻断，断路器（`rm -rf /`/`rm -rf ~`）最后一步拦截；其余全部放行，包括受保护路径                                 |

> - **`auto`** 受账户计划/模型/提供商限制，**第三方 API 未必可用**，本文不展开。
>
> - 任意模式都压不住 **deny / 显式 ask**。

### 1.3.2 设定权限模式的三种途径

模式不是只能靠一个开关——有三种途径，作用域和持久性不同：

| 途径                        | 写在哪                                    | 作用域                                                       | 持久？       |
| ------------------------- | -------------------------------------- | --------------------------------------------------------- | --------- |
| `permissions.defaultMode` | `settings.json` → `permissions` 对象下的字段 | 每次启动的**初始模式**                                             | 持久（写在文件里） |
| `--permission-mode xxx`   | 命令行启动参数                                | 单次会话**覆盖** `defaultMode`                                  | 一次性       |
| `Shift+Tab` / `Alt+M`     | 会话中按键                                  | 当次会话**临时切换**，循环 default→acceptEdits→plan→已启用的 auto/bypass | 一次性       |

**途径一：`defaultMode`（settings.json 字段）**

它是 `settings.json` 里 `permissions` 对象下的一个字段，决定启动时的初始模式。示例：

```json
{
  "permissions": {
    "defaultMode": "acceptEdits"
  }
}
```

**合法取值**：`default` / `acceptEdits` / `plan` / `auto` / `dontAsk` / `bypassPermissions`（就是 1.3.1 那六种）。

**注意**：项目/本地级里写 `"auto"` 会被**直接忽略**（v2.1.142+，防仓库给自己授权）；云会话（Claude Code on the web）里 `"dontAsk"`、`"bypassPermissions"` 都被忽略。要稳妥就放**用户级** `~/.claude/settings.json`。

它设的是「开机起点」，不是「运行时锁死」——会话中仍可 `Shift+Tab` 临时切，但关掉重开又回到 `defaultMode`。

**途径二：`--permission-mode`（CLI 参数）**

```bash
claude --permission-mode plan      # 这次会话用 plan，不管 defaultMode 设了什么
```

**合法取值**：同上六种——`default` / `acceptEdits` / `plan` / `auto` / `dontAsk` / `bypassPermissions`。另外两个旁路 flag：

- `--dangerously-skip-permissions`：等价于 `--permission-mode bypassPermissions`（同一个东西，旧名）。
- `--allow-dangerously-skip-permissions`：只把 bypass **加入 Shift+Tab 循环**、不立即激活（见途径三）。

`--permission-mode` 优先级高于 `defaultMode`（CLI 参数 > settings）；也能配 `-p` 用于非交互模式。

**途径三：`Shift+Tab`（运行时）**

会话中临时切。**基础循环是 `default → acceptEdits → plan`**；`auto` 与 `bypassPermissions` 属于**可选模式**，启用后才会插入循环（排在 `plan` 之后，`bypass` 在前、`auto` 在后）。三者进入条件不同：

- **`auto`**：账户满足要求时（见 1.3.1）自动出现，首次切到会弹一次 opt-in。
- **`bypassPermissions`**：必须靠**启动参数**启用——`--permission-mode bypassPermissions`、`--dangerously-skip-permissions`（二者等价），或 `--allow-dangerously-skip-permissions`（只把该模式加入循环、不立即激活）。从一个**未带启用参数**的会话里，无法靠 `Shift+Tab` 进入 bypass。
- **`dontAsk`**：**永远不在循环里出现**，只能靠 `--permission-mode dontAsk` 启动进入。

## 1.4 PreToolUse Hook 前置拦截

> 环节①（前置拦截）：权限提示**之前**，先跑用户注册的 hook。

PreToolUse hook 在权限提示弹出前运行，输出可 deny / 强制提示 / 跳过提示。但 **hook 决定不绕过权限规则**：

- deny 和 ask 规则照常评估，与 hook 返回无关。
- 匹配的 deny 阻止调用，匹配的 ask 仍提示——即使 hook 返回了 allow/ask。
- **退出码 2 的阻塞 hook 优先于 allow 规则**：在权限规则评估前就拦下，即使有 allow 规则也阻止。

典型用法：把 `Bash` 放 allow 列表跑全部命令，再注册 PreToolUse hook 拒绝少数危险命令——实现「全允许 + 黑名单」，比手写一堆 deny 规则灵活。

**注册方式**：hook 同样写在 `settings.json` 的 `hooks` 对象下（分层合并，见 1.2.2），按事件名分组，每条用正则 `matcher` 匹配工具名：

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          { "type": "command", "command": "~/.claude/hooks/guard.sh" }
        ]
      }
    ]
  }
}
```

`matcher` 是**正则**（部分匹配工具名，如 `Bash`、`Bash|Edit`，留空则匹配全部）；`type` 目前只有 `command`，可选 `timeout`（秒）。配好后也能在 CLI 里用 `/hooks` 命令查看。脚本从 **stdin 收到一段 JSON**（关键字段 `tool_name`、`tool_input`），再用**退出码 + stdout** 控制处置：

| 方式 | 效果 |
|------|------|
| 退出码 0、无输出 | 不干预，走正常权限流程 |
| 退出码 0 + JSON `permissionDecision: "deny"` | 阻止调用，`permissionDecisionReason` 反馈给 Claude |
| 退出码 0 + JSON `permissionDecision: "ask"` | 强制弹提示 |
| 退出码 2 + stderr | blocking error，stderr 返给 Claude、调用被阻止 |

要做"黑名单拦截"优先用 `permissionDecision: "deny"`（语义清晰、reason 可读）；退出码 2 的 stderr 是**给 Claude 看的错误**，不是给用户的弹窗。一个守卫脚本（`~/.claude/hooks/guard.sh`，需 `jq`）：

```bash
#!/usr/bin/env bash
cmd=$(jq -r '.tool_input.command // ""')
if echo "$cmd" | grep -qE 'rm -rf /|git push|curl'; then
  jq -n --arg r "黑名单命令，被 PreToolUse 拦截" \
    '{hookSpecificOutput:{hookEventName:"PreToolUse",permissionDecision:"deny",permissionDecisionReason:$r}}'
fi
exit 0
```

把 `Bash` 放 allow、这个 hook 兜底——长任务里危险命令被拦、其余零打扰。

## 1.5 规则三态与评估顺序

> 环节②（硬约束层，优先于模式③）：在所有层级合并后的规则集上，按固定顺序评估。规则命中 deny/ask 时，连 `bypassPermissions` 都压不住。

`settings.json` 的 `permissions` 对象：

```json
{
  "permissions": {
    "allow": ["Bash(npm run test:*)"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Read(./.env)", "Bash(curl *)"]
  }
}
```

三条评估铁律：

1. **顺序：deny → ask → allow**，首个匹配即定论，**特异性不改变顺序**。
2. 匹配的 `ask` 即使有更具体的 `allow` 同时匹配，**仍询问**。
3. **裸工具名 deny**（如 `Bash`）把工具从模型 context **完全移除**——模型看不见它，无从调用；**作用域 deny**（如 `Bash(rm *)`）保留工具，但阻止匹配调用。

## 1.6 实用组合：两套拿来就能用的搭配

### 1.6.1 安全放手编辑：`acceptEdits` + 受保护路径

`acceptEdits` 自动批准工作目录内的文件编辑，以及 `mkdir`/`touch`/`mv`/`cp`/`rm`/`rmdir`/`sed` 等文件系统命令，**唯独受保护路径例外**——写 `.git`、`.claude`、shell rc（`.bashrc`/`.zshrc`）、`.npmrc`、`.mcp.json`/`.claude.json` 等关键文件时仍提示。

受保护路径的目的是防 **"repository state"（仓库状态）** 和 **"Claude's own configuration"（Claude 自身配置）** 被意外损坏。开 `acceptEdits` 跑长任务，agent 能自由改代码，却**没法静默地**改仓库历史、给自己加 allow/bypass、写 shell rc 做跨会话持久化、或劫持 `.gitconfig`。安全的放手编辑。

```json
{ "permissions": { "defaultMode": "acceptEdits" } }
```


### 1.6.2 受控的危险模式：`bypass` + `deny`

`bypass` 跳过所有提示**和安全检查**（含受保护路径，自 v2.1.126 起也放行），几乎一切立即执行。仍能拦住的只剩三样：**`deny` 规则直接阻断**、**显式 `ask` 规则仍提示**、**断路器**（`rm -rf /`、`rm -rf ~` 针对根/home 本身的删除仍提示，防模型手滑）。

实战套路：在隔离环境（容器/VM）里开 bypass，再配一个 `deny` 黑名单锁死最危险的操作：

```json
{
  "permissions": {
    "deny": [
      "Bash(git push *)",
      "Bash(curl *)",
      "Bash(rm -rf /*)",
      "Read(./.env)",
      "Read(~/.ssh/**)"
    ]
  }
}
```

## 1.7 沙箱：OS 级兜底

> 环节④（OS 兜底，仅 Bash）：权限放行后，OS 层对 Bash 再拦一道。沙箱与权限是互补两层——权限管所有工具，沙箱只管 Bash 的 OS 级强制。

```json
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "autoAllowBashIfSandboxed": true,
    "excludedCommands": ["docker *"],
    "filesystem": {
      "allowWrite": ["/tmp/build", "~/.kube"],
      "denyWrite":  ["/etc", "/usr/local/bin"],
      "denyRead":   ["~/.aws/credentials"],
      "allowRead":  ["."]
    },
    "network": {
      "allowedDomains": ["github.com", "*.npmjs.org"],
      "deniedDomains":  ["*.evil.com"],
      "allowLocalBinding": true
    }
  }
}
```

要点：

- **平台**：仅 macOS / Linux / WSL2，**原生 Windows 不支持**（需在 WSL2 发行版里跑）。macOS 用内置 Seatbelt；Linux/WSL2 依赖 `bubblewrap` + `socat`（缺包时 `/sandbox` 面板会提示安装）。
- `enabled: true` 开启。`failIfUnavailable: true` 启动时沙箱起不来就报错退出（managed 部署用）。
- `autoAllowBashIfSandboxed: true`（默认）——沙箱边界替代整工具提示：裸 `Bash` ask 规则被忽略。但**内容作用域 ask**（`Bash(git push *)`）仍提示，显式 deny 仍生效，`rm`/`rmdir` 针对 `/`/home/关键系统路径仍提示。
- `allowUnsandboxedCommands: false`（默认 true）——彻底禁用 `dangerouslyDisableSandbox` 逃生口，企业强制沙箱用。开启时若命令因沙箱限制失败，Claude 会分析失败并**可能用 `dangerouslyDisableSandbox` 重试**（重试走常规权限流、需批准）。
- `excludedCommands`：列出**必须在沙箱外跑**的命令（如 `docker *`、`git`，或 `gh`/`gcloud`/`terraform` 这类 Go 系 CLI 在 macOS Seatbelt 下 TLS 验证失败时）。
- 网络代理：`network.allowUnixSockets`（放行 SSH agent 等套接字——⚠️ 放行 `/var/run/docker.sock` 等于把宿主机交给容器）、`network.allowLocalBinding`（macOS 绑 localhost 端口）、`network.httpProxyPort`/`socksProxyPort`（自带代理）。`enableWeakerNestedSandbox`（Linux 无特权容器内降级，**降低安全性**）。
- **合并规则**：沙箱 `filesystem.denyWrite/denyRead` 与 Edit/Read 的 deny 规则**合并**入最终边界（数组跨所有 scope 合并，非替换）；网络规则与 WebFetch 规则合并。即使提示注入绕过模型决策，沙箱仍拦住 Bash 越界。

**文件系统路径前缀语法**（注意：与 Read/Edit 规则**不同**！）：

| 前缀 | 含义 | 例 |
|------|------|----|
| `/path` | **绝对路径**（文件系统根） | `/tmp/build` |
| `~/path` | home 目录 | `~/.kube` |
| `./path` 或无前缀 | 项目根（项目级配置）或 `~/.claude`（用户级配置） | `./output` |

> ⚠️ 这套前缀**与 Read/Edit 规则相反**：Read/Edit 里 `//path` 才是绝对、`/path` 是项目相对；沙箱里 `/path` 直接是绝对、没有 `//`。两套语法混用会出错。
