# Claude Code使用技巧——权限设计

> 规划了一个长任务，结果总是需要授予权限而不能脱身；
> 授予完全权限又害怕删盘跑路……

Anthropic 官方工程博客披露：用户实际批准了 **93%** 的权限提示。社区把这种状态命名为 **permission fatigue（权限疲劳）**——「几秒钟点一次批准，最后你根本不读就批了」，这本身就是安全风险。
**「全权放手又怕删盘」** ——  `--dangerously-skip-permissions` 模式**清空了 home 目录、抹掉整台 Mac**；**删了生产数据库记录**，这些都是真实的事故。

其实如今的 Claude Code 权限系统在**两端之间提供多个档位**，只要善于利用，就可以做到解脱于权限确认，也不怕事故出现，能够大大提升长任务的效率和安全性。

## 1.1 一次工具调用的权限流程

权限规则由 Claude Code（**harness层**）强制执行，**不是由模型决定**。这是整个权限设计的根基。

一次工具调用（如 `Bash("rm -rf /tmp/x")`）从发起到执行，权限系统按以下顺序介入：

```
                    一次工具调用
                         │
                         ▼
              ┌─────────────────────┐
              │ ① PreToolUse hook   │  前置拦截
              │    （拦不住规则）    │  但拦不住 deny/ask 规则
              └─────────┬───────────┘
                        │
                        ▼
              ┌─────────────────────┐
              │ 受保护路径闸门      │  硬编码 carve-out
              │ （非 bypass 时）    │  写 .git/.claude 等
              │ 早于规则、压过allow │  bypass 放行此格
              └─────────┬───────────┘
                        │
                        ▼
              ┌─────────────────────┐
              │ ② 规则评估          │  硬约束层
              │  deny → ask → allow │  压过一切模式
              └─────────┬───────────┘
                        │
            ┌───────────┴───────────┐
            ▼ 命中规则               ▼ 没命中任何规则
   deny→阻止 / ask→询问      ┌─────────────────────┐
   allow→放行                 │ ③ 权限模式（兜底）  │  决定"无规则时"
                              │  bypass/acceptEdits │  的默认处置
                              │  /default/dontAsk   │
                              └─────────┬───────────┘
                                        │
                                        ▼
                              ┌─────────────────────┐
                              │ ④ 沙箱兜底（仅Bash）│  OS 级强制
                              └─────────┬───────────┘
                                        │
                                        ▼
                                  执行 / 阻止
```

- **受保护路径 = 硬编码 carve-out**：写 `.git`/`.claude` 等关键路径，acceptEdits 等放权模式也照样提示——检查早于规则、allow 压不过。bypass 放行此格。详见 1.3.4。
- **规则 = 硬约束**：deny/ask 永远生效，**压过一切模式**。这就是为什么 `ask` 规则即使在 `bypassPermissions` 下也照样弹询问，`deny` 更是任何模式都拦不住。
- **模式 = 兜底默认**：只在"没命中任何规则"时决定怎么办。它不"挡在前面"，而是给 allow 之外的工具一个默认处置。

**权限与沙箱是两层互补防御**：

- **权限**——控制 Claude 能用哪些工具、访问哪些文件/域。作用于**所有工具**（Bash、Read、Edit、WebFetch、MCP 等）。
- **沙箱**——OS 级强制，限制 **Bash 工具**的文件系统与网络访问。仅作用于 Bash 及其子进程。

## 1.2 settings.json 与分层配置

### 1.2.1 权限管理都在 settings.json 里

Claude Code 的所有权限配置都写在 `settings.json` 里，权限相关的字段集中在顶层 `permissions` 对象下：

```json
{
  "permissions": {
    "defaultMode": "acceptEdits",        // 权限模式（见 1.3）
    "allow": ["Bash(npm run test:*)"],   // 规则三态（见 1.5）
    "ask":   ["Bash(git push *)"],
    "deny":  ["Read(./.env)"],
    "additionalDirectories": ["../docs/"]
  },
  "sandbox": { "enabled": true }         // 沙箱（见 1.8）
}
```

前面 1.1 流程里的模式、规则，后面各节讲的沙箱、企业策略，本质上都是配置这个文件的不同字段。

### 1.2.2 它不是「一个文件」，是分层的一组文件

最容易误解的点：`settings.json` 不止一个。Claude Code 按固定层级读取多个、合并生效：

```
managed settings    企业强制，最高优先级，无法被覆盖
       ↓
用户级  ~/.claude/settings.json            你这台机器的全局配置
       ↓
项目级  <项目>/.claude/settings.json       随仓库走，团队共享，进版本控制
       ↓
本地级  <项目>/.claude/settings.local.json 个人覆盖，gitignore，不进版本控制
```

**分层的意义**——让不同稳定性的配置各归各位：

| 层级 | 路径 | 适合放 |
|------|------|--------|
| 用户级 | `~/.claude/settings.json` | 你所有项目通用的偏好 |
| 项目级 | `.claude/settings.json` | 跟代码库绑定的团队策略（进 git，团队共享） |
| 本地级 | `.claude/settings.local.json` | 个人临时覆盖（gitignore，不污染团队） |

## 1.3 权限模式与设定途径

> 环节③（兜底层）：规则没命中时，由权限模式决定默认处置——放行 / 询问 / 拒绝。

### 1.3.1 六种模式

根据官方文档，`settings.json` 中 `permissions.defaultMode` 字段决定 Claude Code 启动时的**初始权限模式**，共有六个可选值，沿自主性↔安全性分布如下：

```
自主性低（安全）                                              自主性高（放手）
dontAsk ── default ── plan ── acceptEdits ── auto ── bypassPermissions
```

| 模式                  | 行为                                                                                                         |
| ------------------- | ---------------------------------------------------------------------------------------------------------- |
| `dontAsk`           | 只放行 `permissions.allow` 规则集里的，未预批准的工具**自动拒绝**，连问都不问                                                        |
| `default`           | 每个工具首次使用时询问                                                                                                |
| `plan`              | 只读，**不编辑源文件**（写操作被禁，非询问）                                                                                   |
| `acceptEdits`       | 自动接受工作目录或 `additionalDirectories`目录中的文件编辑命令、 固定的文件系统命令（`mkdir`/`touch`/`mv`/`cp`/`rm`/`sed` 等）；其他 Bash 仍询问 |
| `auto`              | 分类器自动批准多数工具调用，后台安全检查验证动作符合请求（**研究预览**）                                                                     |
| `bypassPermissions` | 跳过所有提示（仅断路器例外）                                                                                             |

### 1.3.2 设定权限模式的三种途径

模式不是只能靠一个开关——有三种途径，作用域和持久性不同。理解它们的关系才能回答「我设的模式为什么不生效 / 只生效一次」：

| 途径                        | 写在哪                                    | 作用域                                                       | 持久？       |
| ------------------------- | -------------------------------------- | --------------------------------------------------------- | --------- |
| `permissions.defaultMode` | `settings.json` → `permissions` 对象下的字段 | 每次启动的**初始模式**                                             | 持久（写在文件里） |
| `--permission-mode xxx`   | 命令行启动参数                                | 单次会话**覆盖** `defaultMode`                                  | 一次性       |
| `Shift+Tab` / `Alt+M`     | 会话中按键                                  | 当次会话**临时切换**，循环 default→acceptEdits→plan→已启用的 auto/bypass | 一次性       |

**途径一：`defaultMode`（settings.json 字段）**

它是 `settings.json` 里 `permissions` 对象下的一个字段，决定启动时的初始模式。示例：

```json
{
  "permissions": {
    "defaultMode": "acceptEdits"
  }
}
```

可写在任一 settings 层级（用户级 / 项目级 / 本地级，见 1.7）。它设的是「开机起点」，不是「运行时锁死」——会话中仍可 `Shift+Tab` 临时切，但关掉重开又回到 `defaultMode`。

**途径二：`--permission-mode`（CLI 参数）**

```bash
claude --permission-mode plan      # 这次会话用 plan，不管 defaultMode 设了什么
```

优先级高于 `defaultMode`，但只活那一次。

**途径三：`Shift+Tab`（运行时）**

会话进行中临时切。`bypassPermissions` 不能靠 `Shift+Tab` 进入，必须靠启动参数 `--dangerously-skip-permissions`。

### 1.3.3 危险模式的项目级防护：auto vs bypassPermissions

`auto` 和 `bypassPermissions` 都是高自主模式，但 harness 防「仓库给自己授予」的机制**完全不同**——这是最易混淆的点：

| | `auto` | `bypassPermissions` |
|--|--------|---------------------|
| 项目级设 `defaultMode` 会怎样 | **值被直接忽略**（等于没设） | 值**不忽略**（可以设） |
| 防护机制 | 值层面抹掉——不让你设 | 值层面放行 + 进入时**强制弹确认提示** |
| 项目级能否跳过这个拦截 | （值都没了，无从跳） | 不能——`skipDangerousModePermissionPrompt` 在项目级**被忽略** |
| 成熟度 | **research preview**（研究预览） | 稳定（行为完全确定） |

**为什么 auto 是 research preview**：其他模式都是纯规则（没有判断，只有 if-else），而 `auto` 引入了一个**待验证的新组件**——后台安全检查在判断「动作是否符合你的请求」，判断准不准还在研究，所以整个模式被标预览，且限制最严（项目级直接忽略值）。`bypassPermissions` 虽危险，但行为确定（就是跳过提示），不算预览。

**这个新组件的内部架构未公开**：分类器究竟是用一个独立微调的小模型、还是复用 Claude 自身做评估、还是两者组合——官方未完整披露。但机制上的关键点是确定的：它用**语义判断**替代了规则层的**模式匹配**。正是这一替代，既让它能批 allow 列里没有的调用（auto 的核心能力），也带来规则层不存在的不确定性——**判断会出错，而 if-else 不会**。

**`skipDangerousModePermissionPrompt` 的一个推断（待实测）**：文档只点名它在 **project**（`.claude/settings.json`）里被忽略，未提 **local**（`.claude/settings.local.json`）。按 local 代表「本人意愿、不随仓库传播」的逻辑，它在 local 级**可能生效**。建议实测：分别在两个文件放 `skipDangerousModePermissionPrompt: true`，看哪个能让启动时不弹确认。

**`bypassPermissions` 的断路器**（bypass 也不是无限制）——官方定位为 **"against model error"（防模型手滑）**，bypass 下仍提示的只有两条：

- `rm -rf /`、`rm -rf ~` 等针对**文件系统根或 home 目录本身**的删除
- 显式 `ask` 规则匹配的调用

注意它**只挡字面意义的根/home**：`rm -rf ~/Documents` 这类子目录删除、覆写/清空文件、`git reset --hard`、DB 操作，全不挡。bypass 明确声明「offers no protection against prompt injection or unintended actions」——这就是有断路器仍会出事的原因。至于受保护路径（`.git`/`.claude` 等）在 bypass 下**也不拦**（自 v2.1.126 起放行），那是另一套机制——见 1.3.4。

仅用于容器/VM 等隔离环境。

### 1.3.4 受保护路径（protected paths）

受保护路径**不是断路器**，而是一道 **carve-out（例外）**：在 acceptEdits / auto 这类**已大范围放权**的模式里，agent 默认"想写哪写哪、不问"。受保护路径从这片自由区圈出一小撮"一旦被乱写后果严重"的路径，单独拉出来仍需确认。文档原话——防 **"repository state"（仓库状态）** 和 **"Claude's own configuration"（Claude 自身配置）** 的意外损坏。

**各模式下的处置（官方表）：**

| 模式 | 受保护路径写入 | 对比该模式本来行为 |
|------|--------------|----------------|
| `default` | 提示 | 本来就什么都问；意义在 allow 压不过 |
| `acceptEdits` | **提示** | ⭐ acceptEdits 本该全自动接受，唯独这些例外 |
| `plan` | 提示 | plan 本就只读，写已禁（重复） |
| `auto` | 交分类器 | 不直接提示，交分类器判断 |
| `dontAsk` | 拒绝 | allow 列外本就拒（一致） |
| `bypassPermissions` | **放行** | 豁免（见下） |

**acceptEdits 那格是整个机制存在的理由**——没有它，开 acceptEdits 跑长任务时 agent 能静默地：

- 写 `.git/`（改 HEAD/refs）→ 仓库状态损坏，丢提交、毁历史
- 写 `.claude/settings.json` → **改自己的权限配置**，给自己加 allow/bypass——提示注入的经典攻击面
- 写 `.bashrc`/`.zshrc`/`.profile` → **持久化**，下次开终端就执行，跨会话存活
- 改 `.gitconfig`/`.gitmodules` → 劫持 push 目标、塞恶意 submodule

**受保护路径清单：**

- 目录：`.git`、`.config/git`、`.vscode`、`.idea`、`.husky`、`.cargo`、`.devcontainer`、`.yarn`、`.mvn`、`.claude`（除 `.claude/worktrees`）
- 文件：`.gitconfig`、`.gitmodules` + shell rc（`.bashrc`/`.bash_profile`/`.zshrc`/`.profile` 等）

**allow 规则压不过它**：检查**早于规则评估**——`allow: ["Edit(.claude/**)"]` 也不顶用，非 bypass 模式照样提示。防的就是"仓库给自己开后门"。

**为什么 bypass 豁免**：bypass 契约是"跳过所有提示和安全检查、立即执行"，且官方钉死**仅用于隔离容器/VM**。一次性容器里 `.git`/`.claude` 本就可丢弃，carve-out 被整体抬起以保零打断——**自 v2.1.126 起 bypass 放行受保护路径写入**（更早版本还提示）。受保护路径只在你真机上的真仓库里有意义。

### 1.3.5 禁用特定模式（企业/自律）

`permissions.disableBypassPermissionsMode: disable` 禁用 bypass + `--dangerously-skip-permissions`；`permissions.disableAutoMode: disable` 禁用 auto。放 managed settings 最有效（无法被覆盖），但任意 scope 都生效——用户也能在自己 settings 里锁死自己。

## 1.4 PreToolUse Hook 前置拦截

> 环节①（前置拦截）：权限提示**之前**，先跑用户注册的 hook。

PreToolUse hook 在权限提示弹出前运行，输出可 deny / 强制提示 / 跳过提示。但 **hook 决定不绕过权限规则**：

- deny 和 ask 规则照常评估，与 hook 返回无关。
- 匹配的 deny 阻止调用，匹配的 ask 仍提示——即使 hook 返回了 allow/ask。
- **退出码 2 的阻塞 hook 优先于 allow 规则**：在权限规则评估前就拦下，即使有 allow 规则也阻止。

典型用法：把 `Bash` 放 allow 列表跑全部命令，再注册 PreToolUse hook 拒绝少数危险命令——实现「全允许 + 黑名单」，比手写一堆 deny 规则灵活。

## 1.5 规则三态与评估顺序

> 环节②（硬约束层，优先于模式③）：在所有层级合并后的规则集上，按固定顺序评估。规则命中 deny/ask 时，连 `bypassPermissions` 都压不住。

`settings.json` 的 `permissions` 对象：

```json
{
  "permissions": {
    "allow": ["Bash(npm run test:*)"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Read(./.env)", "Bash(curl *)"]
  }
}
```

三条评估铁律：

1. **顺序：deny → ask → allow**，首个匹配即定论，**特异性不改变顺序**。
2. 匹配的 `ask` 即使有更具体的 `allow` 同时匹配，**仍询问**。
3. **裸工具名 deny**（如 `Bash`）把工具从模型 context **完全移除**——模型看不见它，无从调用；**作用域 deny**（如 `Bash(rm *)`）保留工具，但阻止匹配调用。

## 1.6 规则语法

> 环节②的匹配细节：一条规则到底匹不匹配这次调用。格式 `Tool` 或 `Tool(specifier)`。

### 1.6.1 匹配工具全部用法

裸工具名（无括号）匹配该工具所有调用，作为 deny 时等同移除工具：`Bash`/`Bash(*)` 等价；`WebFetch` 匹配所有抓取；`Read` 匹配所有文件读。

### 1.6.2 Bash 规则

`*` 跨任意字符（含空格），可出现在命令任意位置：

| 规则 | 匹配 |
|------|------|
| `Bash(npm run build)` | 精确命令 |
| `Bash(npm run test *)` | 以 `npm run test` 开头 |
| `Bash(git * main)` | `git checkout main`、`git push origin main` 等（一个 `*` 跨多参数） |
| `Bash(* --version)` | 以 `--version` 结尾 |

**空格敏感（易错）：**

- `Bash(ls *)`——前缀后必须是**空格或字符串结尾**（词边界），匹配 `ls -la`，不匹配 `lsof`。
- `Bash(ls*)`——无空格，无词边界约束，`ls -la` 和 `lsof` 都匹配。
- 尾部 `:*` 等价于 `空格*`：`Bash(ls:*)` ≡ `Bash(ls *)`。**`:*` 仅在模式末尾识别**；`Bash(git:* push)` 中的冒号是字面量，不匹配 git 命令。

**复合命令：** harness 识别 shell 分隔符（`&&`、`||`、`;`、`|`、`&`、`,`、换行），每条子命令**独立匹配**。批准复合命令选「Yes, don't ask again」时，为每条需批准的子命令**单独存规则**（最多 5 条），而非整条字符串。如批准 `git status && npm test` 存 `npm test` 规则，未来任意位置的 `npm test` 都放行。

**进程包装器剥离：** 匹配前剥离固定包装器 `timeout`、`time`、`nice`、`nohup`、`stdbuf`、无 flag 的 `xargs`。故 `Bash(npm test *)` 也匹配 `timeout 30 npm test`。**此列表内置，不可配置**。开发环境运行器（`direnv exec`、`devbox run`、`mise exec`、`npx`、`docker exec`）**不在列表**——它们把后续参数当命令执行，`Bash(devbox run *)` 会匹配到 `devbox run rm -rf .`，需为每个内部命令写精确规则。`watch`/`setsid`/`ionice`/`flock` 及带 `-exec`/`-delete` 的 `find` **总是提示**，前缀规则无法自动批准。

**只读命令集（内置，各模式都不提示，不可配置）：** `ls`、`cat`、`echo`、`pwd`、`head`、`tail`、`grep`、`find`、`wc`、`which`、`diff`、`stat`、`du`、`cd` + 只读 git。要对其提示需加 ask/deny 规则。

> ⚠️ **安全边界**：Read/Edit 规则只约束内置文件工具和 harness 认得的 Bash 文件命令（`cat`/`head`/`tail`/`sed`）。对**自己打开文件的子进程**（Python/Node 脚本）无效——要 OS 级封堵必须开沙箱。
>
> ⚠️ **URL 约束脆弱**：`Bash(curl http://github.com/ *)` 无法阻止 `curl -X GET`、`https://`、重定向、变量、额外空格等变体。可靠做法：deny 掉 `curl`/`wget`，改用 `WebFetch(domain:github.com)`。

### 1.6.3 Read / Edit 规则

Edit 规则覆盖所有内置编辑工具；Read 规则尽力应用于 Grep、Glob、`@file` 提及、IDE 选中文件。两者遵循 gitignore 语义，4 种锚点：

| 模式 | 含义 | 例 |
|------|------|----|
| `//path` | 文件系统根绝对路径 | `Read(//Users/alice/secrets/**)` |
| `~/path` | home 目录 | `Read(~/Documents/*.pdf)` |
| `/path` | **项目根**（非系统根！） | `Edit(/src/**/*.ts)` |
| `path` 或 `./path` | 当前目录 | `Read(*.env)` |

- `*` 匹配**单段**（不含 `/`），`**` 跨目录。
- 裸文件名按 gitignore 语义**任意深度**匹配：`Read(.env)` ≡ `Read(**/.env)`，但只匹配当前目录及子目录，不匹配父目录或其他项目。要全盘用 `Read(//**/.env)`。
- `/Users/alice/file` **不是**绝对路径，是相对项目根；绝对路径必须 `//` 开头。
- Windows 路径归一化为 POSIX（`C:\Users\alice` → `/c/Users/alice`），全盘用 `//**/.env`。

**符号链接双路径检查：** 访问符号链接时检查链接本身和目标两条路径。**allow** 需两者都匹配（否则提示）；**deny** 任一匹配即阻止。例：`Read(./project/**)` 允许 + `Read(~/.ssh/**)` 拒绝时，`./project/key → ~/.ssh/id_rsa` 的链接被阻止（目标违反 allow 且匹配 deny）。

### 1.6.4 WebFetch 规则

`domain:` 前缀，匹配 hostname，大小写不敏感，支持 `*`：

| 规则 | 匹配 |
|------|------|
| `WebFetch(domain:example.com)` | example.com |
| `WebFetch(domain:*.example.com)` | 任意深度子域（`api.example.com`、`a.b.example.com`），**不含根域** example.com |
| `WebFetch(domain:*)` | 所有域（≡ 裸 `WebFetch`） |

- `*` 跨 `.` 仅在**开头的 `*.` 或整个模式**时；否则限单标签。`WebFetch(domain:github.*)` 匹配 `github.io` 不匹配 `github.evil.com`（攻击者可注册）。
- 同列表内精确规则与通配规则都匹配同一 hostname 时，**精确规则胜出**（但评估顺序不变：deny 仍先于 ask/allow）。

### 1.6.5 MCP / Agent / PowerShell / Cd

- **MCP**：`mcp__server`（该 server 全部工具）、`mcp__server__*`（同义通配）、`mcp__server__tool`（具体）。server 名为 Claude Code 中配置的连接名。
- **Agent**：`Agent(Explore)`、`Agent(Plan)`、`Agent(my-custom-agent)`——控制可用子代理，放 deny 数组或用 `--disallowedTools`。
- **PowerShell**：同 Bash 形态（`:*` 等价、`*` 任意位置）。别名规范化（`Get-ChildItem` 规则也匹配 `gci`/`ls`/`dir`），大小写不敏感，AST 解析复合命令。
- **Cd**：控制 `/cd` 可移动到的目录（模型不可调用，仅用户 `/cd` 时生效）。加任意 `Cd` allow 规则即切换为**白名单模式**；`*` 单段、`**` 跨段。

### 1.6.6 工具名位置的通配

`deny`/`ask` 接受工具名位置的 glob：`*` 匹配所有工具，`mcp__*` 匹配所有 MCP 工具，被裸名 glob deny 匹配的工具从 context 移除。

`allow` 仅在**字面 `mcp__server__` 前缀后**接受 glob（server 段不能含通配）：`mcp__github__get_*` 合法。**未锚定的 allow glob**（`*`、`B*`、`mcp__*`）被跳过并警告，不自动批准任何东西。

工具名含 `_` 或 `*` 的规则豁免"未知工具"拼写检查。

## 1.7 配置层级与优先级

> 环节②的规则集从哪来：多个 settings 文件合并，按固定优先级叠加。这是 1.2.2 分层机制的细化——谁压谁。

```
Managed settings  (不可被任何级别覆盖，含 CLI 参数)
       ↓
CLI 参数           (--allowedTools / --disallowedTools，临时会话)
       ↓
本地项目            .claude/settings.local.json
       ↓
共享项目            .claude/settings.json
       ↓
用户级              ~/.claude/settings.json
```

**铁律：任意级别 deny → 其他级别无法 allow。** Managed deny 连 `--allowedTools` 都压不住。跨方向也成立：用户级 deny 压制项目级 allow，因为 deny 始终先于 allow 评估。

### 1.7.1 实战：与 cc-switch 共存

settings **不是单一文件，是一组分层文件**（见 1.2.2）。cc-switch 管的是**用户级** `~/.claude/settings.json`（供应商端点、key、模型——这些确实该随时切）。但权限规则跟着供应商切没意义，还会被 cc-switch 覆盖。

把权限挪到**不随供应商切的层**：

| 文件 | 谁管 | 适合放 |
|------|------|--------|
| `~/.claude/settings.json`（用户级） | **cc-switch 切** | 供应商/端点/模型 |
| `.claude/settings.json`（项目级，进版本控制） | 你 / 团队 | **项目通用权限规则**（团队共享） |
| `.claude/settings.local.json`（项目本地，gitignore） | 你个人 | **个人权限偏好**（不共享） |

cc-switch 切供应商时只动用户级那个文件；权限规则在项目级文件里不受影响。两者靠合并机制叠加，项目级优先级 > 用户级。

> ⚠️ **`defaultMode` + `auto` 的坑**：若想把 `defaultMode` 挪到项目级用 `auto`——行不通，`auto` 在项目级被忽略（只认用户级，而用户级正被 cc-switch 管）。其他模式放项目级没问题。

## 1.8 沙箱：OS 级兜底

> 环节④（OS 兜底，仅 Bash）：权限放行后，OS 层对 Bash 再拦一道。沙箱与权限是互补两层——权限管所有工具，沙箱只管 Bash 的 OS 级强制。

```json
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "autoAllowBashIfSandboxed": true,
    "excludedCommands": ["docker *"],
    "filesystem": {
      "allowWrite": ["/tmp/build", "~/.kube"],
      "denyWrite":  ["/etc", "/usr/local/bin"],
      "denyRead":   ["~/.aws/credentials"],
      "allowRead":  ["."]
    },
    "network": {
      "allowedDomains": ["github.com", "*.npmjs.org"],
      "deniedDomains":  ["*.evil.com"],
      "allowLocalBinding": true
    }
  }
}
```

要点：

- `enabled: true` 开启（macOS/Linux/WSL2）。`failIfUnavailable: true` 启动时沙箱起不来就报错退出（managed 部署用）。
- `autoAllowBashIfSandboxed: true`（默认）——沙箱边界替代整工具提示：裸 `Bash` ask 规则被忽略。但**内容作用域 ask**（`Bash(git push *)`）仍提示，显式 deny 仍生效，`rm`/`rmdir` 针对 `/`/home 仍提示。
- `allowUnsandboxedCommands: false`（默认 true）——彻底禁用 `dangerouslyDisableSandbox` 逃生口，企业强制沙箱用。
- **合并规则**：沙箱 `filesystem.denyWrite/denyRead` 与 Edit/Read 的 deny 规则**合并**入最终边界（数组跨所有 scope 合并，非替换）；网络规则与 WebFetch 规则合并。即使提示注入绕过模型决策，沙箱仍拦住 Bash 越界。

## 1.9 安全防护机制

> 横切层：贯穿全流程的防护，不是某个环节，而是弥漫在规则、模式、沙箱每一层的设计原则。

### 1.9.1 默认只读 + 写入限制

- 默认严格只读权限。编辑文件、跑测试、执行命令需显式许可。
- harness 内建只读命令集（见 1.6.2）各模式都不提示。
- **写入限制**：Claude 只能写**启动目录及其子目录**。可读工作目录外的文件（访问系统库/依赖），但写操作严格限于项目范围。要扩展用 `additionalDirectories`、`--add-dir`、`/add-dir`。

### 1.9.2 prompt injection 防护

- **权限系统**：敏感操作需显式批准。
- **上下文感知分析**：分析完整请求检测潜在有害指令。
- **输入净化**：处理用户输入防命令注入。
- **网络命令默认询问**：`curl`/`wget` 等取网络内容的命令默认不自动批准，像普通非只读 Bash 一样提示。可 `Bash(curl *)` 允许或 `deny` 全禁。
- **隔离 context window**：WebFetch 用独立 context window，避免注入恶意提示。
- **信任验证**：首次运行某代码库、新 MCP server 需信任验证。`-p` 非交互模式下禁用。在 home 目录启动时信任只限当前会话（不落盘），应从项目子目录启动。
- **fail-closed 匹配**：未匹配的命令默认要求手动批准。
- **命令注入检测**：可疑 bash 命令即使已被 allowlist 也要求手动批准。

### 1.9.3 Windows WebDAV 风险（坑）

Windows 上**不建议启用 WebDAV**，也不让 Claude Code 访问 `\\*` 等可能含 WebDAV 子目录的路径。WebDAV 已被微软因安全风险弃用，启用后可能让 Claude Code 触发对远程主机的网络请求，**绕过权限系统**。

## 1.10 企业策略：managed-only

> 横切层：仅从 managed settings 读取、放用户/项目 settings 无效的键，用于组织级强制策略。

| 设置 | 作用 |
|------|------|
| `disableBypassPermissionsMode: disable` | 禁 bypass + `--dangerously-skip-permissions` |
| `disableAutoMode: disable` | 禁 auto |
| `allowManagedPermissionRulesOnly: true` | 用户/项目不得定义 allow/ask/deny，只认 managed |
| `allowManagedMcpServersOnly: true` | 只认 managed 的 `allowedMcpServers`（deny 仍跨级合并） |
| `allowManagedHooksOnly: true` | 只加载 managed/SDK/强制启用插件的 hook |
| `sandbox.filesystem.allowManagedReadPathsOnly: true` | 只尊重 managed 的 allowRead |
| `sandbox.network.allowManagedDomainsOnly: true` | 非白名单域自动拒绝（不询问） |

`disableBypassPermissionsMode` 虽放 managed 最有效，但任意 scope 都生效——用户可在自己 settings 里锁死自己。
